01

What the rule is

In plain terms

CMS is forcing health plans to expose their data — and their prior authorization process — through standard APIs, so that software can do in seconds what people currently do with a phone and a fax machine.

CMS-0057-F, the CMS Interoperability and Prior Authorization rule, contains more than prior authorization. It mandates four APIs:

APIWhat it does
Patient AccessLets a patient pull their own claims, encounters and clinical data into an app they choose.
Provider AccessLets a treating provider pull a patient's data from the plan.
Payer-to-PayerMoves a member's history when they change plans.
Prior AuthorizationThe big one, and the subject of this page.

The deadline is January 1, 2027, and it is directed at health plans — in the words, those serving under Medicare Advantage, CHIP, and fee-for-service programs. But the practical scope is wider than the list of regulated entities, because plans rarely build this themselves: they subcontract to vendors and business associates who end up implementing the actual APIs.

The assessment is worth repeating, because it sets the stakes:

This is one of the most radical transformations in terms of prior authorization and the clinical workflow since the original HIPAA ruling for portability came on. CMS-0057-F Explained
02

Who it actually touches

CMS regulates plans directly. It reaches providers by a different route: not a mandate, but a MIPS measure. Under the Improving Prior Authorization score there is an electronic prior authorization measure, and by calendar year 2027 a MIPS-eligible clinician must attest that they have completed at least one electronic prior authorization — using a certified health IT product.

That certification is where HTI-4 comes in. It added new criteria sitting just beneath the existing (g)(10) standardized FHIR API criterion — numbered (g)(31), (g)(32) and (g)(33) — covering provider prior authorization, coverage requirements discovery, documentation templates and rules, and prior authorization support.

Check the mapping yourself

It lists these criterion numbers quickly and the exact criterion-to-standard mapping is easy to garble. Treat (g)(31)–(g)(33) as “the new prior-auth certification criteria, immediately below (g)(10)” and confirm which is which against the regulation before you scope work against a specific number.

Context matters here: (g)(10) is the criterion the federal government has already been enforcing against EHRs that block information by failing to expose FHIR APIs. The new criteria sit in that same enforcement neighbourhood.

03

Why this is not just a faster fax

The old process has a hidden first step that nothing ever standardised: finding out that prior authorization was needed at all. In the description, someone at the provider carries it in their head — these CPT codes, for this plan, need prior auth — then calls, then faxes, then waits.

When the payer did not support the X12 transactions, it was worse: the provider logged into that plan's own portal and filled in a form, per patient, hundreds of times a day. Reducing that is precisely what CMS means by burden reduction.

Two other things changed

  • The clock. CMS is cutting decision time to 72 hours for expedited requests, with proposals to shorten it further to 48.
  • X12 278 became optional. HIPAA had required covered entities to use the X12 278 transaction for prior authorization. CMS is applying enforcement discretion: if you have implemented the newer FHIR standards, they will not pursue you for HIPAA non-compliance merely because you skipped X12.
04

The foundation: CDS Hooks

In plain terms

Ordinary APIs wait to be called. CDS Hooks runs inside the doctor's workflow — at the moment an order is being placed — and puts an answer on screen before they finish.

All three prior-auth standards are built on CDS Hooks, and the implementation guide is emphatic that this is what makes them different in kind rather than degree. The EHR gets in the way of the practitioner's workflow at a defined moment, calls out to a service, and renders what comes back as cards — critical alerts, warnings, or suggestions such as consider a different drug.

The round trip takes 5 to 10 seconds, and under a second when the service is well cached. That creates a feedback loop between practitioner and health plan that simply did not exist before, when the same answer took days or weeks.

The two phases

CDS Hooks has a setup phase and a runtime phase, and they happen at completely different times.

Discovery response — what the service advertises

GET https://payer1.com/cds-services

{
  "services": [
    {
      "hook":        "order-select",
      "id":          "coverage-check",   // → POST /cds-services/coverage-check
      "title":       "Coverage Requirements Discovery",
      "prefetch": {
        "patient":  "Patient/{{context.patientId}}",
        "coverage": "Coverage?patient={{context.patientId}}"
      }
    },
    { "hook": "order-sign", "id": "final-check", ... }
  ]
}

Invocation — what the EHR then posts

POST https://payer1.com/cds-services/coverage-check

{
  "hookInstance":      "d1577c69-dfbe-44ad-ba6d-3e05e953b2ea",
  "hook":              "order-select",
  "fhirServer":        "https://ehr.example.org/fhir",
  "fhirAuthorization": { "access_token": "...", "expires_in": 300 },
  "context": {
    "userId":      "Practitioner/abc",
    "patientId":   "1288992",
    "encounterId": "89284",
    "selections":  ["ServiceRequest/103"],
    "draftOrders": { "resourceType": "Bundle", ... }
  },
  "prefetch": {
    "patient":  { "resourceType": "Patient", ... },   // already fetched
    "coverage": { "resourceType": "Bundle", ... }
  }
}

Prefetch, and why it exists

The service could use fhirServer and fhirAuthorization to call the EHR back for whatever it needs. Prefetch is the faster path: during discovery the service declares which resources it will want, templated against the hook's context, and the EHR resolves them before it posts.

The guidance is direct — avoid calling back if you can prefetch instead, because every callback eats into a budget measured in seconds.

You can only template what the hook actually carries

Prefetch templates reference the hook's own context fields. Asking for draftOrders in a patient-view hook is meaningless — that field only exists on order-select. Check the hook definition before writing the template.

The hooks that matter

HookWhen it firesMaturity
order-selectAfter the clinician selects an order, before signing it.most mature
order-signImmediately before the order is finalised.most mature
order-dispatchWhen an order is sent on to its performer.useful
appointment-bookWhen an appointment is being booked.useful
patient-viewWhen the patient's chart is opened.broad
allergyintolerance-createWhen an allergy is recorded.niche

The shortcut: implement order-select, order-sign, order-dispatch and appointment-book and you are “pretty much covered”.

05

CRD, DTR and PAS

Three profiles in the Da Vinci specification, each picking up where the last leaves off. What makes the design work is that each one happens in a different place.

CRD — Coverage Requirements Discovery

A CDS Hooks service, run by the payer. It answers the questions nobody could previously ask:

  • Is this covered by the patient's plan?
  • Is prior authorization required?
  • If so, which documents are needed — and a link or questionnaire to start with.

It can also suggest alternative or additional therapy, correct the coverage the EHR holds if it is out of date, and push down a questionnaire the EHR does not yet have.

The worked scenario from the implementation guide

Mrs Jones, 35, presents with a new-onset headache. Dr Good is concerned about an intracranial process and wants a head CT. As Dr Good begins filling out the order, the EHR calls the CRD server run by Mrs Jones' payer, passing the patient, her coverage, and the order. Within a few seconds the server replies that a prior authorization is required, lists the additional clinical documents needed — a progress note, prior studies — and provides the form.

The notes that older versions of the guide describe launching a separate app here; newer CRD versions simply return the questionnaire into the EHR and let DTR handle it.

DTR — Documentation Templates and Rules

The payer returns a standardised FHIR questionnaire, and the practitioner fills it in inside the EHR. No separate portal, for one form, for one plan, for one patient. Fields are autofilled wherever the EHR already holds the answer, so the practitioner only supplies what the plan genuinely does not know.

This is the single largest piece of burden reduction in the whole rule — and, the standard with the worst name.

PAS — Prior Authorization Support

Once the questionnaire is complete, the EHR assembles a prior authorization packet and submits it to the plan. The EHR can then query its status, or — better — the plan pushes a notification through a FHIR Subscription when a decision is ready, so nobody has to poll.

06

What a CRD service can return

The response is not a yes or no. It is a set of possible actions, and a real implementation will use several of them.

ResponseMeaning
Covered?Whether the plan covers this procedure or item for this patient at all.
Prior auth required?The core question. Often the only one the clinician reads.
Documentation neededWhich documents must accompany the request, plus links or the questionnaire itself.
Launch DTRHand the EHR a specific questionnaire to open.
Suggest an alternativeA different therapy that is covered, or needs no authorization.
Suggest additional therapySomething that should accompany the order.
Update coverageCorrect the coverage record the EHR is holding, if it is stale.
Inform onlyContext with no action — for example, that the lab test was already run and here are the results.

What-if hooks

CRD also supports a no-op or “what-if” scenario: the clinician is not really placing an order, they are checking what would happen if they did. Many EHRs are building this.

Treat these differently

On a what-if request, make no stateful change and issue no real authorization number. Answer the question — covered, authorization needed, documents required — and record nothing. There is a way to detect it in the request; a payer that misses this will hand out authorization numbers for orders that were never placed.

07

If you are a plan with vendors

In plain terms

Do not invent a private API for each vendor. Have every vendor implement the public spec exactly, and put a thin facade of your own in front of them.

This is the question, that says comes up most often: a health plan has several vendors handling different plans or different code sets, and nobody knows who implements what. The answer is that these APIs are composable.

Ask each vendor to implement CRD exactly as though they were talking to an EHR directly. Then build a facade in front that presents one endpoint to the EHR and routes behind it. Each vendor can validate itself independently against the Inferno testing suite and the CDS Hooks sandbox — the same tests you will be measured by.

The token rule that shapes the architecture

CRD's privacy and security section is explicit, and it drives the whole design:

Access tokens provided as part of CDS calls should not be forwarded to systems that are not managed by the same organization or have business associate agreements that allow centralized audit of access. Possible alternatives to token sharing include routing all requests for information through the initial endpoint system. CRD implementation guide, privacy and security

In practice: the fhirAuthorization token that arrives with a hook is meant for that EHR, from you. Do not pass it on. Instead, host your own FHIR server for your vendors and proxy their reads back to the EHR yourself. There is a practical reason too — the EHR's FHIR server is frequently on an internal network your vendor could not reach anyway.

Aggregate discovery

When an EHR asks what you support, you do not want to advertise ten different order-select services. Call each vendor's discovery endpoint yourself, unify the result, and publish one set of CDS services under your own base URL.

Namespace the prefetch

Each vendor will declare its own prefetch requirements, and two of them will inevitably want a key called patient. Prefix each vendor's keys before passing them to the EHR, then strip the prefix and route each vendor only its own resolved resources. The prefix style does not matter — an underscore is fine — only that it is consistent.

What you advertise, and what each vendor gets back

// what the EHR sees in YOUR discovery response
"prefetch": {
  "vendorA_patient":   "Patient/{{context.patientId}}",
  "vendorA_coverage":  "Coverage?patient={{context.patientId}}",
  "vendorB_patient":   "Patient/{{context.patientId}}",
  "vendorB_encounter": "Encounter/{{context.encounterId}}"
}

// what you forward to Vendor A — prefix stripped, nothing else included
"prefetch": {
  "patient":  { "resourceType": "Patient", ... },
  "coverage": { "resourceType": "Bundle", ... }
}
08

Which version, and how to prove it works

Two CRD version numbers, and they differ

CMS mandates CRD 2.0.1. What EHRs are actually implementing is 2.2.1. It recommendation for anyone building CRD, DTR or PAS is to build against 2.2.1 — it satisfies the mandate and matches what you will be talking to.

Testing

  • Inferno — the testing kit you will be measured against. It has dedicated suites for CRD. Point every vendor at it independently.
  • The CDS Hooks sandbox — quicker for checking discovery responses and card rendering while you are still iterating.

What to do now

  1. Establish which programs you are covered under, and therefore whether January 1, 2027 binds you directly or through a client.
  2. Build CDS Hooks discovery and one hook — order-select — end to end before anything else. Everything downstream depends on it.
  3. Decide the prefetch set early. It is the difference between a one-second response and a five-second one, and it is declared in discovery, so changing it later means re-coordinating with every EHR.
  4. Draw your trust boundary before you sign vendor contracts. Who holds the EHR's token, and whose FHIR server do vendors talk to?
  5. Make every vendor implement the public spec and pass Inferno on their own. Compose, do not invent.
  6. Handle what-if requests from day one, so you never issue an authorization number for an order nobody placed.

The one thing to take away

This is not a faster version of the old prior authorization. The old process could not begin until somebody already knew that authorization was needed — and nothing in the system ever answered that question. It lived in a person's memory, or a phone call.

CRD makes that question an API call that returns in seconds, inside the workflow, before anyone has committed to anything. DTR and PAS are the cleanup. Discovery is the change.
