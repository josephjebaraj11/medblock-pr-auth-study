A virtual employee that collects the money and gets the authorization — so staff only see what's actually stuck.

This walkthrough covers two connected agents built for physician practices and outpatient rehab centers: VICE, which chases unpaid insurance claims, and ClearAuth AI, which secures prior authorization before a procedure is ever scheduled. Both follow the same principle — electronic first, portal second, a phone call only when nothing else resolves it, and a human for anything that isn't administrative.

01 / The problem we're solving

Two kinds of money get stuck for the same reason — nobody is chasing them fast enough.

A claim sits at "pending" for 47 days because no one called to ask why. A procedure waits because prior authorization takes a staff member 20–40 minutes of hold music per case. Neither problem is hard to solve — it's just repetitive, phone-heavy, and easy to fall behind on when it competes with patient care.

Point solutions already exist for pieces of this, but each covers only part of the loop:

Market reference points
Gateway EDI / TriZetto
The clearinghouse layer most practices already run on — claims, ERA/remittance, real-time eligibility, claim status, authorizations. Electronic only; it does not call anyone.
Infinx
Closest existing example of an end-to-end agent — claim-status follow-up, prior auth, eligibility, payment posting, denials — connected through payer portals, APIs and clearinghouses.
Operator Labs
Focused specifically on the phone-call piece: AI agents that navigate IVRs, hold, and talk to payer reps to get claim status and denial reasons.
Waystar (AltitudeAI)
A much larger enterprise revenue-cycle platform moving toward autonomous claims, denials, appeals and prior auth — built for scale, not a small practice's day-to-day queue.

None of them are built as a single agent that a small practice just hands its outstanding A/R and its physician orders to, and says: handle it, and only bring me what actually needs a decision. That's the gap VICE and ClearAuth AI are built to close — sitting above the clearinghouse the practice already has, not replacing it.

02 / Integration points

One agent, eight systems it has to move between.

Every claim or authorization the agent touches passes through some combination of these eight integration points. None of them are optional — the agent is only as good as its weakest connection, so each one gets its own credentials, its own failure handling, and its own place in the audit log.

These eight are what ClearAuth AI and VICE need. A different client will have a different EHR, a different clearinghouse, maybe no clearinghouse at all — Section 06 covers how the platform treats each of these as a swappable connector rather than a fixed integration.

03 / What we have to reference & manage

Owning this loop means owning the operational knowledge behind it, not just the code.

The integrations above are the pipes. What actually keeps the agent accurate day to day is a set of living references that someone has to own, update, and audit — otherwise the agent starts making calls with stale information.

Static knowledge — changes slowly, must be reviewed on a schedule
Payer requirement matrix
Which payers require prior authorization for which CPT codes. This shifts by payer and by plan, and is the single biggest source of stale-data errors if left unreviewed.
IVR call maps & rep scripts per payer
The "press 2 for claim status" trees, typical hold patterns, and the phrasing that gets a straight answer from a payer rep — captured once, reused every call.
Auto-action policy thresholds
The practice's own rules for what the agent may submit or appeal automatically versus what always needs a signature — set by the client, not assumed by us.
Living operational state — changes every day
Credential & access vault
Clearinghouse, payer portal, and EHR credentials — scoped per payer, rotated on schedule, never shared across integrations.
Escalation runbook
Which staff member handles clinical-necessity questions, peer-to-peer review calls, and denials that don't fit the standard decision tree.
Audit trail — write-once, kept for dispute resolution
Reference/transaction number ledger
Every claim or auth reference number the agent is given, tied back to the exact call, portal submission, or EDI transaction that produced it.
Call recordings & transcripts
Kept against the practice's retention policy — the only way to resolve a dispute over what a payer rep actually said.
04 / How we solve it

Cheapest channel first. A phone call is the last resort, not the first move.

Every claim and every authorization request runs down the same waterfall. Electronic checks are near-instant and cost nothing; a phone call is slow and only happens when nothing electronic could resolve it. Humans only ever see what's left over at the bottom.

VICE — full swimlane. The same waterfall, now traced across every participant so it's clear who — or what system — is active at each step, and exactly where a human has to step in.

05 / Solution architecture

The agent sits above what the practice already runs — nothing to rip out.

The bottom layer is the practice's existing systems of record, untouched. Everything above it is new: a connector layer that speaks EDI and drives browser/portal automation, a voice engine for the calls electronic channels can't resolve, an orchestration layer that runs the waterfall and enforces policy, an audit layer that write-locks every action, and a thin human interface for the exceptions.

This is ClearAuth AI and VICE's specific deployment of a general shape: layer 2, the connector layer, is built so that a different client's EHR or clearinghouse plugs into the same core without changing it — the architecture principle behind that is Section 06.

06 / Platform strategy

ClearAuth AI and VICE are the first two agents on a platform — not the platform itself.

Every future client will run a different EHR, a different clearinghouse, a different set of payer portals — sometimes none of the above. The platform has to absorb that variation without a rewrite per client, which means one architectural rule is non-negotiable: the orchestration core is closed for modification; the connector layer is open for extension. A new client's system becomes a new connector implementing the same interface — never a fork of the core, never a conditional branch buried in the decision engine. If adding a client ever means changing the orchestration engine, the audit layer, or the dashboard, that's the architecture failing, not the client being unusual.

Startups

Fast, minimal, self-serve

A single connector set, multi-tenant SaaS by default, self-serve onboarding, usage-based pricing with no minimum commitment.

SMBs

This document's scope

A handful of connectors — one EHR, one clearinghouse, a few payer portals — multi-tenant SaaS, a guided onboarding with a short Discovery pass (Section 10).

Enterprise

Custom, isolated, dedicated

Larger connector counts, custom connector development, dedicated or fully air-gapped deployment (Section 09), its own SLA and its own compliance review before go-live.

API

API connector

Direct, versioned API — the fastest and most reliable option when a system offers one.

MCP

MCP connector

Model Context Protocol — structured, permissioned tool calls for agent actions, not just data reads.

WEB

Browser / scraping connector

Drives a payer portal or legacy web UI directly when no API exists — the fallback, not the default.

HOOK

Webhook / event connector

Real-time pushes from a client system instead of polling, where the source system supports it.

SFTP

File / batch connector

Scheduled file drops — 835 remittance batches, nightly exports — for systems that only speak in files.

Similar to how Claude ships a directory of ready-made connectors a user just switches on, the platform ships with a growing library of pre-built connectors for the EHRs, clearinghouses, and payer portals already integrated. Onboarding a new client checks that library first (Section 08) — new connector code is the exception that gets contributed back to the library, not a one-off thrown away after the project.

07 / Product roadmap

MVP1, then MVP2 — proven internally before it's sold.

The platform gets built by building two real agents on it, not by building a platform in the abstract. ClearAuth AI and VICE run first for the first client (or internally) — only once both hold up under real volume does the platform open to the market described in Section 06.

MVP1

ClearAuth AI

Implement, deliver, and deploy the prior-authorization agent first — proves the connector framework and the audit/compliance model end-to-end on one workflow before a second is added.

MVP2

VICE

Implement and deliver the claims-collection agent on the same core — the real test of the platform's own claim: a second agent, a second set of connectors, zero changes to the orchestration core.

Phase 3

Internal validation

Both agents run for the first client, or internally — real volume, real exceptions, a real audit trail — hardening the platform before any other client's data touches it.

Phase 4

External market launch

The platform opens to new clients across the startup / SMB / enterprise segments; onboarding runs through the guided questionnaire (Section 08) instead of a bespoke integration project.

Why internal-first

Building MVP1 and MVP2 for the first client (or internally) first means the compliance model, the audit trail, and the connector interface all get proven under our own accountability before a paying client's data runs through them. Selling the platform is the second business; running it well ourselves is what makes the second business credible.

08 / Onboarding

A new client becomes a working tenant — not a bespoke integration project.

Onboarding is itself a platform requirement, not a services engagement done once per client. A new client answers a guided questionnaire about their systems and their deployment needs; the platform matches those answers against the connector library from Section 06 — new connector development is the exception path, not the default one.

09 / Tenancy & administration

Every client owns their tenant. Some own the whole box.

Two deployment shapes have to work from day one, and both share the same three-tier admin model underneath.

Default

Multi-tenant SaaS

Platform-hosted, shared infrastructure, strict per-tenant logical data isolation. Fastest to onboard, usage-metered — the default for startups and most SMB clients.

On request

Air-gapped / dedicated

Deployed inside the client's own environment — on-prem or their private cloud — with no external network dependency. Same core, same connector framework, chosen where compliance posture requires full isolation.

Master Admin — the platform operator
Onboards new client tenants
Runs the Section 08 process for each new client.
Manages the shared connector registry
Adds new connectors once, available to every tenant afterward.
Sees cross-tenant usage and health
Never PHI — volume, uptime, and exception-rate metrics only.
Tenant Admin — the client's own admin
Manages their tenant's users and roles
Invites staff, assigns billing / front-desk / clinical personas.
Configures their own rules
Auto-submit thresholds, escalation routing, payer-matrix overrides — through the platform's rules engine, not a code change.
Views their own full audit log
Every action inside their tenant, exportable on request.
End User — the client's staff
Logs in to their own persona
Sees only their role's queue and exceptions — nothing cross-tenant, nothing outside their permission.
Rules live in configuration, not code

Auto-submit thresholds, escalation routing, and payer-requirement overrides are set by each Tenant Admin through the platform's own rules engine. Changing a threshold is a configuration change with its own audit entry — never a code deployment, and never something only we can do on the client's behalf.

10 / Discovery

We can't design your waterfall from the outside. Discovery is where we learn how the job is actually done today.

Every payer-requirement matrix, IVR script, and auto-submit threshold in Section 03 has to come from somewhere real — not a template. Discovery is a set of working sessions with the people who currently do this job (billing, prior-auth coordinators, front desk), plus a hard look at the systems and volume behind them. The practice pays for what the agent actually does — a quiet week costs less to run than a busy one. Discovery is what sizes what "busy" looks like for your volume; no cost figures appear until that sizing is done.

13 / Compliance & guardrails

The agent does the paperwork. It never makes the medical call.

This is the boundary the whole design is built around: administrative and procedural work is fully automatable; medical judgment is not. Every guardrail below exists to keep that line firm and provable.

HIPAA
PHI moves through EHR data, call transcripts, and clinical documents. A signed BAA is required with every subprocessor in the chain — the voice platform, hosting provider, and any model API — before PHI touches the system.
Call disclosure
The agent identifies itself as an automated representative only where the payer permits it; the payer-requirement matrix has to track which payers accept this versus require a human caller.
Recording consent
Outbound calls are recorded for the audit trail. Consent rules vary by state (one-party vs. two-party) and by payer — this has to be checked per call, not assumed.
No medical judgment
Medical necessity, peer-to-peer review, and unusual denials always escalate to a licensed staff member. The agent reports facts and missing documentation — it does not decide whether a procedure is justified.
Audit trail
Every electronic check, portal submission, and call is logged with a timestamp, source, and reference number — the same record used for both compliance review and payer disputes.
Data handling
PHI encrypted at rest and in transit; retention follows the practice's existing HIPAA policy rather than a separate schedule.
Access control
The exception dashboard and audit log are role-restricted — front-desk, billing, and clinical staff see only what their role needs.
Client IP & ownership
Every case record, configured rule, and document a tenant creates belongs to that client — exportable on request, and never used to train a model shared across other tenants without explicit opt-in.
Tenant isolation
Logical isolation per tenant in the multi-tenant SaaS deployment, physical isolation in the air-gapped deployment (Section 09) — a breach or bug in one tenant can't cross into another's.
Configurable rules
Auto-submit thresholds and escalation routing are set by each Tenant Admin, not hardcoded per client — every rule change is itself an audited, versioned event.
14 / Next steps

Start narrow. Prove the waterfall before widening it.

The recommended first pilot is one workflow, one payer set, and a shadow period before anything submits automatically — so the practice can see the agent's decisions before trusting it to act on them unsupervised.

Phase 1

Pick one workflow

Either VICE (claims follow-up) or ClearAuth AI (prior auth) — not both at once — scoped to your highest-volume payer.

Phase 2

Shadow mode

Agent runs the full waterfall and proposes every action, but a human approves each one before it goes out — validates accuracy against real cases.

Phase 3

Supervised auto-submit

Low-risk actions (electronic checks, routine reprocessing requests) go live automatically; appeals and anything over the client's threshold still route to a person.

Phase 4

Widen scope

Add payers, add the second workflow, and raise auto-submit thresholds only as the exception rate proves the agent is trustworthy.

What this means for the first working session

We'll start with Discovery (Section 10) to map current-state process and volume, then confirm the access and policy items from Section 11. Everything else — the waterfall logic, the integrations, the audit trail — is the part we build; the practice's job is mostly the decisions only it can make.
