1. Executive decision: what InfiniAI should build for Cascade AI

Do not build two separate agents. Build a small Healthcare Revenue Execution Platform with ClearAuth and VICE as the first two agent products. The differentiation is a single case/workflow model that chooses the best channel — electronic transaction/API first, portal/browser second, voice third — and escalates only true exceptions.

Differentiator #1

Electronic-first execution

Use clearinghouse/API/FHIR whenever possible because it is faster, cheaper, structured and auditable. Use portals and voice only when the electronic lane cannot resolve the case.

Differentiator #2

One workflow, many channels

The case remains the same even if execution moves from API → portal → phone → human. This avoids point-bot fragmentation.

Differentiator #3

Progressive onboarding

Customer can start with CSV/SFTP or REST in days, then graduate to bidirectional FHIR/HL7/API integrations without redesigning the product.

Differentiator #4

Observable autonomy

Every decision, submission, payer response, call, retry, document and human action becomes part of the audit trail and operational analytics.

Source alignment: the attached requirement explicitly describes the desired operating model as “give the AI the outstanding A/R and tell it: collect the money,” with electronic claim-status first, portals/APIs second, phone only when needed, and humans receiving exceptions. ClearAuth follows the same pattern for prior authorization.

278

Prior authorization

Legacy HIPAA service-review transaction. Modern FHIR PAS implementations can translate to/from X12 278 depending on intermediary/payer.

276 / 277

Claim status

Core VICE electronic-first status path before phone follow-up.

837 / 835

Claims / remittance

Useful later for corrected claim/resubmission, payment posting and recovery analytics. Do not make this required for MVP1.

9. Customer onboarding experience

The fastest path to revenue is a tiered onboarding model. Do not require a deep EHR integration before the customer sees value.

Track A • Fast Start

File-first

Target: days to 2 weeks. SFTP/CSV/standard extracts in; dashboard + actions out. Best for pilot and smaller practices.

Track B • Connected

REST / FHIR

Target: 2–6 weeks. Bidirectional API integration, webhooks, documents and writeback. Exact timing depends on customer IT and vendor registration.

Track C • Clearinghouse

EDI + enrollment

Target: variable. X12/API connectivity can be quick technically, but payer enrollment and transaction approval can take weeks.

Track D • Enterprise

Deep workflow

Target: multi-week. Epic/Oracle interfaces, SSO, custom policies, security review, dedicated UAT and release governance.

12. Competitive research notes that materially change the roadmap

Infinx — why it is the closest model
Infinx publicly positions Healthcare Revenue OS as a multi-agent operating system rather than a single automation. Its stated layers include AI/automation, RCM experts, payer integration, provider integration, security/compliance, workflow execution, human-in-the-loop/workforce orchestration and analytics. Its provider integration page explicitly lists API/webhooks, HL7, FHIR-ready patterns, secure file exchange and RPA; its payer connectivity page lists APIs, EDI/clearinghouses, portals, SFTP/batch and normalized writeback. This strongly supports building InfiniAI’s shared platform services before multiplying agents.
Operator Labs — what to copy, and what not to copy
Copy the execution behaviors: queue prioritization, IVR navigation, hold handling, structured call outcomes, automatic callbacks, escalation and writeback. Do not make the product voice-centric. The attached client goal and broader competitors imply electronic-first orchestration; voice is the fallback channel for cases that APIs/EDI/portals cannot resolve.
Waystar — where the long-term moat comes from
Waystar’s scale and 2026 agentic roadmap show the advantage of combining workflow automation with a large normalized transaction/connectivity layer. For InfiniAI, the practical version is a canonical data model plus reusable adapters and payer intelligence, not an attempt to recreate a national clearinghouse in six months.
FHIR timing — why we should be ready but not block MVP1 on it
CMS-0057-F requires impacted payer prior-authorization APIs beginning primarily January 1, 2027, and recommends FHIR R4 with Da Vinci CRD/DTR/PAS implementation guides. Epic has already published 2026 prior-auth API functionality, and TriZetto and Availity are publicly offering FHIR prior-auth capabilities. Therefore the connector architecture should be FHIR-native-ready now, but MVP1 should still support today’s mixed world of REST, X12, portals, SOAP/SFTP and voice.
