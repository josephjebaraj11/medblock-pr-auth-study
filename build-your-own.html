The seven components you would have to write yourself — what each one does in plain terms, what it looks like in code, and the order to build them in.

01Source catalog 02Authorization 03Connection state 04Pull engine 05Storage 06Data out 07Platform shell →Tech stack

How the seven fit together

Six of the components form a single line: you look a system up, get permission, keep track of that permission, fetch the data, store it, and send it on. The seventh wraps around all of them — it is the workspace, the keys and the dashboard that make the other six usable by a team.

1

Source catalog

A directory of every system you can connect to

In simple terms

A phone book of hospitals. Before you can connect a patient to their hospital, you need a list of every hospital and the web address where its data lives.

This is a database of every system you can connect to. A source can have a display name, logo, portal URL, FHIR base URL, vendor type, and setup requirements.

You do not have to gather these by hand. Vendors publish them because regulation requires it: Epic publishes its FHIR endpoints on open.epic.com, and Oracle Health (Cerner) and athenahealth have similar lists. For each endpoint you fetch /.well-known/smart-configuration, which tells you that server's OAuth URLs.

Example — what step 3 returns

GET https://fhir.example-hospital.org/api/FHIR/R4/.well-known/smart-configuration

{
  "authorization_endpoint": "https://fhir.example-hospital.org/oauth2/authorize",
  "token_endpoint":         "https://fhir.example-hospital.org/oauth2/token",
  "capabilities": ["launch-standalone", "client-public", "permission-patient"],
  "code_challenge_methods_supported": ["S256"],
  "scopes_supported": ["openid", "fhirUser", "patient/*.read", "offline_access"]
}

Example — the table it fills

CREATE TABLE sources (
  id              uuid PRIMARY KEY,
  display_name    text NOT NULL,     -- "Example Hospital"
  logo_url        text,
  portal_url      text,              -- where the patient signs in
  fhir_base_url   text NOT NULL,
  vendor          text NOT NULL,     -- epic | cerner | athena | ...
  authorize_url   text,              -- from smart-configuration
  token_url       text,
  scopes          text[],
  setup_notes     text,
  discovered_at   timestamptz
);

2

Authorization layer

The hardest part to get right

In simple terms

Getting permission, and keeping it. Four different people can give you that permission, and each one has its own official procedure you have to follow exactly.

Medblocks supports four patterns, and each maps to a published standard. The pattern you pick is decided by who is able to say yes — not by what is convenient.

The three you can actually build

Patient access uses the SMART on FHIR standalone launch — an ordinary OAuth2 authorization code flow with PKCE. You send the patient to the hospital's authorize URL, they sign in and approve, and you exchange the returned code for tokens.

Example — the authorize URL you send the patient to

https://fhir.example-hospital.org/oauth2/authorize
  ?response_type=code
  &client_id=your-registered-client-id
  &redirect_uri=https://app.yourco.com/auth/smart/callback
  &scope=openid fhirUser patient/*.read offline_access
  &state=OPAQUE_HANDLE          // you look this up on return
  &aud=https://fhir.example-hospital.org/api/FHIR/R4
  &code_challenge=BASE64URL(SHA256(verifier))
  &code_challenge_method=S256

// offline_access is what gets you a refresh token.
// Without it the connection dies the moment the access token expires.

Clinician workflow uses the SMART EHR launch, where your app is opened from inside Epic or Cerner. The EHR hands you a launch parameter carrying the patient context, and you exchange it the same way.

Backend uses SMART Backend Services, which authenticates with a JWT client assertion and the client_credentials grant. No browser, no user, no refresh token — you sign a short-lived JWT with your private key each time.

Example — the backend assertion

// You sign this with your private key; they verify it against your JWKS.
{
  "iss": "your-client-id",
  "sub": "your-client-id",
  "aud": "https://fhir.example-hospital.org/oauth2/token",
  "exp": 1790000300,          // under 5 minutes out
  "jti": "one-time-id"        // replay protection
}

POST /oauth2/token
  grant_type=client_credentials
  &scope=system/Patient.read system/Observation.read
  &client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
  &client_assertion=<the signed JWT>

Network access goes through Carequality, CommonWell, or TEFCA. This requires legal and organizational membership, so leave it out of your first version.

Keeping the permission alive

Store tokens encrypted — AWS KMS or Vault — and run a scheduler that refreshes them before they expire. Refreshing after expiry is often too late, and on servers that rotate the refresh token on every use, a failed write loses the connection permanently.

Example — refresh ahead of time, and persist atomically

// run every few minutes
const due = await db.query(`
  SELECT * FROM connections
  WHERE state = 'active'
    AND access_expires_at < now() + interval '10 minutes'
`);

for (const c of due) {
  try {
    const t = await refresh(c.token_url, decrypt(c.refresh_token));
    // rotated refresh tokens MUST be written before the next attempt
    await db.tx(() => saveTokens(c.id, encrypt(t.access), encrypt(t.refresh)));
  } catch {
    await setState(c.id, 'refresh_failed');   // → emits an event
  }
}

Connection state machine

Five states, and an event on every move

In simple terms

Permission is not permanent. It can be withdrawn, it can quietly stop working, and your app needs to know which of those happened so it can say the right thing to the patient.

Copy the lifecycle directly: active (access works), failed (authorization did not complete), refresh_failed (the refresh token stopped working), expired, and disconnected (access was revoked). Every token refresh and every API error should move the connection into the right state and emit an event.

Example — one place that owns every transition

type ConnectionState =
  | 'authorizing' | 'active' | 'failed'
  | 'refresh_failed' | 'expired' | 'disconnected';

const ALLOWED: Record<ConnectionState, ConnectionState[]> = {
  authorizing:    ['active', 'failed'],
  active:         ['refresh_failed', 'expired', 'disconnected'],
  refresh_failed: ['authorizing', 'disconnected'],
  expired:        ['authorizing'],
  failed:         ['authorizing'],
  disconnected:   ['authorizing'],
};

export async function setState(id, next, reason) {
  const cur = await getState(id);
  if (!ALLOWED[cur].includes(next)) throw new Error(`${cur} → ${next}`);

  await db.tx(async () => {
    await db.update('connections', id, { state: next, reason });
    await db.insert('auth_events', { id, from: cur, to: next, reason });
    await outbox.emit(`connection.${next}`, { connection_id: id });
  });
}

Tech stack for this layer

What you needUseHow
The machine itselfplain TypeScript mapA Record<State, State[]> and one setState() function is genuinely enough. Reach for xstate only if guards and side effects multiply.
Atomic transitionsPostgres transactionState change, audit row and event must commit together or not at all.
Emitting events safelytransactional outbox tableWrite the event to an outbox row in the same transaction, then a poller ships it to the queue. This is what stops the classic bug: state saved, webhook never sent.
Shipping from the outboxBullMQ worker, or Postgres LISTEN/NOTIFYPoll-and-mark is simpler and perfectly fast at this scale.
The audit trailappend-only Postgres tableGrant INSERT only. No UPDATE, no DELETE — an audit log you can edit is not one.
4

Background pull engine

Fetching is not finished when the patient is

In simple terms

Once you have permission, you still have to go and collect the records — and that takes minutes or hours, long after the patient has closed the tab. Real portals hand data over slowly, a page at a time.

After a connection becomes active, you schedule retrieval jobs for the resources that source supports. Those jobs take time because real portals paginate slowly, return large histories, vary in which resources they support, and enforce different rate limits.

What to build it out of

  • A job queue. BullMQ on Redis is enough to start; Temporal is better for long, retryable workflows.
  • Per-source resource lists, read from each server's CapabilityStatement. Typical resources are Patient, Condition, Observation, MedicationRequest, AllergyIntolerance, Immunization, Encounter, DocumentReference.
  • Pagination by following Bundle.link[next], plus per-source rate limiting and exponential backoff.
  • Bulk FHIR ($export) for the backend pattern.
  • A pull monitoring table recording status, counts and errors for each job.

Example — the loop in code

export async function pullResource(conn, resourceType) {
  let url = `${conn.fhir_base}/${resourceType}?patient=${conn.patient_ref}&_count=100`;
  let pages = 0, saved = 0;

  while (url) {
    const res = await limiter(conn.source_id, () => fetchWithToken(url, conn));

    if (res.status === 429 || res.status >= 500) {
      await sleep(backoff(pages, res.headers.get('retry-after')));
      continue;                                // same url, try again
    }

    const bundle = await res.json();
    for (const e of bundle.entry ?? []) {
      await upsertRaw(conn.source_id, e.resource);   // see component 5
      saved++;
    }

    url = bundle.link?.find(l => l.relation === 'next')?.url;  // ← the loop
    pages++;
  }

  await db.insert('pull_runs', { conn: conn.id, resourceType, pages, saved, ok: true });
}

Example — ask the server what it actually supports

// Never assume. Read the CapabilityStatement once per source and cache it.
const cap = await get(`${base}/metadata`);
const supported = cap.rest[0].resource.map(r => r.type);
// → ['Patient','Condition','Observation','MedicationRequest', ...]

for (const type of WANTED.filter(t => supported.includes(t))) {
  await queue.add('pull', { connectionId: conn.id, resourceType: type });
}

Storage and normalization

Keep the raw truth, derive the useful shape

In simple terms

Save exactly what the hospital sent, so you can always prove it. Then build a second, tidier copy on top that your app is actually pleasant to query.

Store raw FHIR resources keyed by source and resource ID so that repeat pulls do not create duplicates, and record where each resource came from. You can use Postgres with JSONB, or run an actual FHIR server internally.

On top of that, add a Clinical Domain Models layer that turns raw FHIR into simpler objects — medications, labs, and so on — with codes mapped to standard terminologies like LOINC, SNOMED and RxNorm.

Example — the table, and why the key matters

CREATE TABLE raw_resources (
  id             bigserial PRIMARY KEY,
  connection_id  uuid NOT NULL,
  source_id      uuid NOT NULL,
  resource_type  text NOT NULL,        -- 'Observation'
  resource_id    text NOT NULL,        -- 'abc' — the SOURCE's id
  body           jsonb NOT NULL,
  fetched_at     timestamptz NOT NULL,
  UNIQUE (source_id, resource_type, resource_id)   -- ← the whole trick
);

-- a re-pull updates instead of duplicating
INSERT INTO raw_resources (...) VALUES (...)
ON CONFLICT (source_id, resource_type, resource_id)
DO UPDATE SET body = excluded.body, fetched_at = excluded.fetched_at;

Example — one raw Observation, and the model derived from it

// RAW — what the hospital actually sent
{ "resourceType": "Observation", "id": "abc",
  "code": { "coding": [{ "system": "http://loinc.org", "code": "4548-4" }] },
  "valueQuantity": { "value": 6.7, "unit": "%" },
  "effectiveDateTime": "2026-08-14T09:12:00Z" }

// DERIVED — what your app queries
{ "kind": "lab",
  "name": "HbA1c",
  "loinc": "4548-4",
  "value": 6.7, "unit": "%",
  "takenAt": "2026-08-14T09:12:00Z",
  "provenance": { "source": "example-hospital", "raw": "Observation/abc" } }

6

Data out

Three delivery methods

In simple terms

Three ways to hand the records over: your app asks for them, you tell your app something happened, or you push a copy into another system automatically.

Direct reads. A records endpoint returns the patient's latest stored resources as a paginated list, where each item names the EHR source it came from.

Webhooks for events such as a patient session completing, a background pull finishing or failing, and a connection losing access and needing the patient to reconnect. Sign each payload with HMAC and retry failed deliveries.

Exports to a FHIR server receiving FHIR R4 resources, or to object storage as NDJSON files in S3-compatible storage, GCS, or Azure Blob. Keep a watermark per destination so each export only sends new data.

Example — sign the webhook, and let the receiver verify it

// sending
const body = JSON.stringify({ id: evt.id, type: evt.type, data: evt.data });
const sig  = crypto.createHmac('sha256', endpoint.secret)
                   .update(`${timestamp}.${body}`).digest('hex');

await fetch(endpoint.url, {
  method: 'POST',
  headers: { 'content-type': 'application/json',
             'x-signature': `t=${timestamp},v1=${sig}` },
  body,
});
// on non-2xx or timeout: requeue with exponential backoff, keep evt.id stable

// receiving — raw body, never the parsed object
const expected = crypto.createHmac('sha256', SECRET)
                        .update(`${t}.${rawBody}`).digest('hex');
if (!crypto.timingSafeEqual(Buffer.from(v1), Buffer.from(expected))) return 400;

Example — NDJSON, one resource per line

# s3://your-bucket/exports/2026-09-26/Observation.ndjson
{"resourceType":"Observation","id":"abc","status":"final", ...}
{"resourceType":"Observation","id":"xyz","status":"final", ...}
{"resourceType":"Observation","id":"def","status":"final", ...}

# one JSON object per line means a consumer can stream the file
# instead of parsing one enormous array into memory.

Example — the watermark makes it a delta

const { watermark } = await db.one(
  `SELECT watermark FROM export_destinations WHERE id = $1`, [dest.id]);

const rows = await db.query(
  `SELECT body FROM raw_resources
     WHERE fetched_at > $1 ORDER BY fetched_at LIMIT 10000`, [watermark]);

await writeNdjson(dest, rows);
await db.update('export_destinations', dest.id,
                { watermark: last(rows).fetched_at });   // only after success

Platform shell

What makes the other six usable by a team

In simple terms

The account system. Somewhere for a team to keep their keys, try things safely before going live, and see what happened when a customer says it is broken.

You also need multi-tenant workspaces with separate sandbox and production modes, API keys, a dashboard, an auth event audit log, and a TypeScript SDK. Adding an MCP server later is optional.

PieceWhat it doesPriority
WorkspacesEvery row in every table carries a workspace id. Sandbox and production are separate workspaces with separate keys.v1
API keysPrefix them by environment so a key is self-describing — sk_live_… and sk_sbx_…. Store only a hash.v1
Auth event logAppend-only record of every authorization attempt: source, outcome, error code, timestamp. This is what support reads.v1
DashboardConnection states, pull history, export runs. Lets non-engineers answer questions without a database client.v1
TypeScript SDKA thin typed wrapper over the REST API. Mostly matters for adoption, not capability.later
MCP serverLets an AI agent operate the workspace. Genuinely optional.later

Example — make tenancy impossible to forget

-- put workspace_id on everything, and let the database enforce it
ALTER TABLE connections ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON connections
  USING (workspace_id = current_setting('app.workspace_id')::uuid);

-- then set it once per request, from the API key
SET LOCAL app.workspace_id = '…';

Build in this order

The components are numbered by dependency, but the fastest route to something real is narrower than building all seven:

  1. One source, end to end. Seed the catalog with a single sandbox (Epic's is the obvious choice), implement the standalone launch, store one token, pull Patient and Observation. Nothing else.
  2. Make it survive. The state machine, proactive refresh, the pagination loop, backoff, and the pull monitoring table. This is what turns a demo into a system.
  3. Make it usable. Workspaces, API keys, the audit log, a webhook or two.
  4. Make it plural. A second and third source — mostly configuration and waiting on registrations, not new code.
  5. Make it mean something. Normalization and terminology mapping, last, once you have real variety to normalise.

One honest caveat

Everything on this page is buildable, and none of it is the expensive part. The expensive part is registration: getting a production app approved by each vendor takes weeks to months, runs on someone else's calendar, and no code shortens it.

So start the paperwork on day one, in parallel with component 1 — and keep network access out of version one entirely, because that one is a membership negotiation rather than a feature.
