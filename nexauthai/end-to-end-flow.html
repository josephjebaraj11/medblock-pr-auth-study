One Authorization,
End to End

A single prior-authorization request followed from the moment a physician clicks one button to the audit record left behind — told twice at every stage: what the person sees, and what actually happens underneath.

How to read this

Every stage below is told through two lenses, and each lens gets its own diagram.

▶ User view

What the person experiences. Who touches it, what they see on screen, and — usually — what they don't have to do. Paired with a user diagram: people and screens, no machinery.

⚙ Under the hood

The mechanism. Which agent role acts, which connector it reaches through, which standard carries it, and how the case's state moves. Paired with a technical diagram: roles, protocols, and the record being written.

One example runs the whole way through, so it reads as a single story: an MRI of the lumbar spine, CPT 72148, ordered for a patient at a multi-specialty practice. Branches — if instead… — appear where they split off, so the main line stays straight.

The one line it never crosses

The agent does the paperwork. It never makes the medical judgment. Medical necessity, peer-to-peer and every denial go to a licensed human. In the prototype this is not a policy statement — it is enforced in the type system and the service layer, and there is no code path that records a denial without a named licensed reviewer.

The journey at a glance

The request runs down a cost-ordered waterfall — electronic first, portal second, a phone call only when nothing else resolves it, and a human only for what isn't administrative.

1

The request starts

One click, and the physician is done

▶ User view

The physician orders an MRI of the lumbar spine and clicks Get Authorization. That is the entire interaction. No form, no portal login, no second system. The practice does nothing further unless something is genuinely missing — in which case it surfaces immediately rather than failing silently three days later.

⚙ Under the hood

The request arrives through the EHR connector — a CDS Hooks order-sign invocation where the EHR supports it, otherwise a POST /v1/requests from an integration. The Orchestrator opens a canonical Case, stamps it with the tenant and an idempotency key (tenant : order : CPT), validates that the packet is complete enough to act on, and writes the first audit entry.

That idempotency key is doing real work. Combined with inquire-before-submit, it is what makes the acceptance criterion zero duplicate authorizations achievable rather than aspirational — ordering the same service twice opens the existing case rather than creating a second one.

2

Is authorization even required?

The electronic check — and the answer nobody assumes

▶ User view

The system answers one of two things. Either “No authorization needed — here is the proof, with the source, the date and a reference number”, and the case stops there. Or “Authorization required — proceeding.”

Nothing is assumed. A “no” that turns out to be wrong is an unpaid claim discovered months later, so a “no” here is an evidenced assertion with a reference number attached — never a default the system fell back to.

⚙ Under the hood

Electronic is the cheapest and fastest lane, and it runs in two parts. First, confirm active coverage via real-time eligibility (X12 270/271). Then determine whether this plan requires authorization for CPT 72148 — through Da Vinci CRD (fired by CDS Hooks) where the payer exposes it, falling through to an X12 278 inquiry, and finally to the versioned payer-requirement matrix.

The Coverage role drives this, backed by a rules layer it looks rules up in rather than recalling them from model memory. The result type is deliberately tri-state — true, false, "unknown" — so that the two-valued shape which would invite a bad default simply does not exist.

If instead no authorization is required: the result, source, date and reference number are written back to the chart and the case closes here. No portal, no call, and nothing for a person to do.

3

Assembling the packet

Document-gathering, and the line about minimum necessary

▶ User view

Nothing visible happens. The agent pulls together exactly what this payer asks for — the order, recent office notes, therapy records, imaging history — and only interrupts a human if genuine clinical evidence is missing.

When it does interrupt, the case arrives as “Clinical review required” with the agent's findings already attached, so the clinician corrects rather than starts from a blank form.

⚙ Under the hood

Where the payer runs Da Vinci DTR, its documentation questionnaire is fetched and auto-fills from the chart — structured fields deterministically via CQL, with document extraction for anything narrative. Where the payer has no DTR, the agent assembles the same packet from the published policy as a checklist instead.

Either way the rule is minimum-necessary by construction: the document fetch is filtered to the types the matched rule actually listed. Prior authorization is a HIPAA payment disclosure, so the treatment exception does not apply and the whole chart must never travel.

Clinical and Compliance roles validate evidence and completeness in parallel. Every extracted answer carries its source document, the span within it, and a confidence figure — so a reviewer checks the agent rather than trusting it.

If instead clinical evidence is missing — say the chart shows four weeks of conservative therapy against a six-week policy threshold — the case is flagged CLINICAL REVIEW REQUIRED and handed to a licensed clinician, pre-filled with the agent's findings. Whether concurrent medication satisfies the criterion's intent is a medical judgement, and the agent does not make it.

4

The assessment and the gate

What the agent concluded, and whether it may act alone

▶ User view

Either the case simply goes, or it lands in the worklist as “Waiting for release” — with the agent's reasoning attached. A staff member reads what it found, and releases or corrects it.

When they open the assessment, four things are there: the facts it extracted and where each came from, how the case scores against every criterion in the payer's policy, anything missing, and a drafted medical-necessity letter that cannot be sent until a person approves it.

⚙ Under the hood

The Decision role consolidates the Clinical and Compliance findings and scores confidence as a weighted vector of six named components, all stored — because a single number is not reviewable.

Then the gate runs three checks, in this order: the tenant kill switch, then the payer's trust mode (Shadow → Supervised → Wider), then the confidence threshold. Any one of them holds the case, and the audit entry names which one did.

Autonomy is granted per payer, per action type and per workflow — never all at once, and promotion to wider autonomy requires explicit written sign-off.

5

Submitting — the waterfall

Cheapest channel first, and every attempt recorded

▶ User view

The staff screen shows “Submitted” with a tracking reference. That is all. Whether it went over an API in a second or took an eight-minute phone call is visible if you look, but it is not something anyone has to care about.

⚙ Under the hood

The Submission role walks the routes available for this payer in cost order, stopping at the first that succeeds. Every attempt is written to the case — including the ones that failed, which is what makes the routing explainable afterwards rather than merely asserted.

A route whose connection is not currently usable is skipped rather than attempted. Before any voice attempt, two checks run: whether this payer permits an automated caller at all, and what the recording-consent rule is in the relevant states. Neither is a default; both are matrix lookups.

On success, a decision-deadline timer starts — 72 hours expedited, 7 calendar days standard.

6

Pended — the mid-review demand

Document-gathering, the second time

▶ User view

Many payers come back part-way through asking for more. The staff member sees a one-line task: “Payer requested one additional document.” They release it, and the agent fetches and sends that specific document.

The request does not start over. Nothing is resubmitted. The position in the payer's queue is not lost.

⚙ Under the hood

A pended response opens a Da Vinci CDex additional-information Task. Where the payer has no CDex, the same thing arrives as a portal notice or as a representative listing the gaps on a call — so the Communication record is channel-agnostic by design.

The Follow-Up role records the reason and reference, retrieves just that permitted document, and fulfils the Task — not a new Claim/$submit. A recheck is scheduled against the decision deadline rather than on a fixed interval.

If the gap turns out to be clinical evidence that does not exist, it routes to clinical review instead. The agent does not decide whether evidence that is absent ought to be created.

7

Inside the payer

Where the decision is actually made Assumption

Read this stage differently

Everything in this stage is an assumption. The source research is entirely provider-side — no client or consulting document describes a payer intake queue, a reviewer workflow or a determination form. This is modelled on payer-side products named in the market research. It is the largest open question in the project, and it should be settled before anyone presents this externally.

▶ User view

Two people, with a hard line between them. The intake reviewer sees a queue with a completeness indicator and a deadline clock, confirms the packet is workable, and triages it. They cannot decide anything clinical.

The clinical reviewer — a medical director — reads the criteria match as an aid, then approves, denies or partially approves. The determination is recorded against their name.

⚙ Under the hood

recordDecision throws if a denial or partial approval arrives without a named reviewer holding the licensed role. An approval returned electronically by a payer legitimately has no human on our side — so the attribution is required exactly where it matters and not where it would be theatre.

The outcome maps onto a FHIR ClaimResponse: complete for an approval, partial where fewer units were granted, error with adjudication reason codes for a denial. Over the X12 lane the same thing is an HCR01 action code — A1, A6, A3, A4.

8

The outcome and the write-back

Five plain statuses — and what happens on a denial

▶ User view

Staff see the result, not the machinery: “MRI L-Spine — APPROVED · Auth # · Valid 26 Aug – 26 Sep · Ref #”. What they ever see is a small, fixed set of statuses:

No authorization required Submitted — pending Approved Clinical review required Expiring soon

Partial approval is a first-class outcome, not a yes-or-no forced into a binary — a payer granting a 90-day rental instead of a purchase, or fewer units than requested, is normal and shown as what it is.

⚙ Under the hood

On approval, the authorization number, valid-from and valid-to dates, units and reference are written back to the EHR, and an expiry timer runs against the scheduled service date.

On denial, the case routes to a licensed human — always, by policy and by code. The agent drafts an appeal citing the evidence that was omitted, but filing requires a clinician's approval. The audit then holds two separate entries: appeal.approved by a user, and appeal.filed by an agent. The human decision and the mechanical action are deliberately not the same record.

9

The record left behind

Long after the fact, every action is explainable

▶ User view

Months later, in an appeal or a payer dispute, someone needs to know exactly what happened and when. They open the case and read it — every electronic check, every portal submission, every phone call, each with a timestamp, a source and a reference number. Calls carry a recording and a transcript.

There is no edit control and no delete control on that screen. There is none in the API either.

⚙ Under the hood

A write-once, hash-chained audit log. Each entry's prevHash is the previous entry's hash, so a removed or altered row is detectable rather than merely discouraged. The viewer verifies the chain on load and states the result plainly instead of implying it with a padlock icon.

Every entry carries an actor and an actor type — user, agent, system or payer — which is what makes “a person decided this” distinguishable from “a process did this” at a glance. In production the application role has UPDATE and DELETE revoked on the table.

The whole journey, in one paragraph

A physician clicks Get Authorization on an MRI order. NexAuthAI opens a case, confirms coverage, and asks the payer electronically whether CPT 72148 even needs authorization — if not, it logs the proof with a reference number and stops. If it does, the agent assembles exactly the clinical packet that payer requires, escalating to a clinician only when real evidence is missing, then submits it the cheapest way that payer supports — electronic, then portal, then a phone call, then a human — without ever creating a duplicate. When the payer asks for more mid-review, it fetches just that document and resupplies it without starting over. The outcome comes back, the authorization number and valid dates are written into the chart, and the practice sees only the result or the one exception that genuinely needs a person. Every step is written once to an audit trail that can be replayed later.

And the agent never, at any point, decides whether the care was necessary.
