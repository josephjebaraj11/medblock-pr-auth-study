openEHR
and FHIR

Before we study Medblocks, we need the common terms used in healthcare. These two standards are the ones everything else is built on.

Part one

What is openEHR?

openEHR is an open standard for storing, exchanging, and managing electronic health records (EHRs) in a way that is interoperable, vendor-neutral, and designed for long-term healthcare data management.

Think of it as

A common language and structure for healthcare data — similar to how HTML provides a standard structure for web pages.

Why was openEHR created?

Traditional healthcare systems often store patient data differently:

The same measurement, three names

  • One hospital stores blood pressure as BP
  • Another stores it as BloodPressure
  • Another stores it in a custom format

This makes sharing and analyzing healthcare data difficult.

openEHR solves this by defining:

  • How clinical data should be structured
  • How it should be stored
  • How different systems can understand the same data

Key concepts

1

Clinical Data Repository (CDR)

The openEHR repository stores patient information in a structured way.

Examples

Patient demographics Lab results Diagnoses Medications Vital signs Clinical notes
2

Archetypes

An archetype is a reusable clinical data model.

Instead of every hospital creating its own blood pressure structure, everyone uses the same archetype.

3

Templates

Templates combine multiple archetypes for a specific use case.

A single clinic visit needs several kinds of measurement at once. The template says which archetypes that visit uses, and in what order.

Part two

What is FHIR?

FHIR — Fast Healthcare Interoperability Resources — is a healthcare data standard created by HL7 International to help different healthcare systems exchange medical information in a consistent way.

It is one of the most widely adopted healthcare interoperability standards today.

Simple explanation

Imagine:

  • Hospital A uses one software system
  • Hospital B uses another
  • The insurance company uses a third
  • The lab uses a fourth

FHIR provides a common API and data format so they can communicate without custom integrations.

Think of FHIR as
Healthcare + REST API + JSON

For developers, it feels very similar to modern web APIs.

Example: Patient resource

FHIR data is organised into resources — self-contained objects like Patient, Observation, Condition or MedicationRequest. Here is the simplest one:

{
  "resourceType": "Patient",
  "id": "123",
  "name": [{
    "family": "Doe",
    "given": ["John"]
  }],
  "gender": "male",
  "birthDate": "1990-01-01"
}

In FHIR, family is the surname and given holds the forenames — given is an array because a person can have several. So this resource describes John Doe. It is an easy pair to swap by accident, and worth getting right early, because every other resource points at patients by id and displays them by name.

Plain JSON, a predictable shape, fetched over ordinary HTTP. That is the entire reason FHIR spread as fast as it did — any developer who has used a REST API already knows how to read it.

Part three

How the two fit together

They are often presented as rivals. They are not — they answer different questions, and a serious platform usually uses both.

 openEHRFHIR
Main questionHow should clinical data be modelled and stored for decades?How should two systems exchange clinical data right now?
StrengthDeep, governed clinical models — archetypes and templatesSimple, developer-friendly API — REST and JSON
Unit of dataArchetype, composed into templatesResource, e.g. Patient, Observation
Typical roleThe record you keepThe message you send
Created byThe openEHR FoundationHL7 International
One way to hold it

openEHR is closer to your database schema — careful, clinically governed, built to outlive the software using it. FHIR is closer to your API layer — the shape data takes when it travels between systems.

Why this matters before studying Medblocks

Medblocks’ own documentation makes a claim that only lands once you know both terms: “FHIR is the transport format, but source data still varies.”

Every US hospital now exposes FHIR — that is the left-to-right arrow in the diagram above, and it is solved. What is not solved is that the same clinical fact arrives from five hospitals in five shapes, five code systems and five units. Medblocks’ answer is a layer they call Clinical Domain Models, sitting above raw FHIR.

That is archetype thinking. Hold both ideas — FHIR for the wire, archetypes for the meaning — and the rest of the Medblocks study reads as one continuous argument instead of a pile of acronyms.
