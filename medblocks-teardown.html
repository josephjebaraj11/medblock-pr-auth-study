Method

A teardown is only as good as its discipline about what it actually knows. This one separates three things that are easy to blur: what was observed, what follows from it, and what merely sounds plausible.

confirmed

Directly observed in a public artifact, or computed from one. Quote it.

inferred

Follows from confirmed evidence with a short, stated reasoning chain. Likely right; not certain.

speculative

Consistent with the evidence but underdetermined. Treat as a hypothesis to test.

Sources used: the public documentation tree at medblocks.com/docs, the public GitHub organisation, a public API directory listing, one public key set the vendor published to a public repository, and the HTTP response body of one unauthenticated request to a path that does not exist.

Sources deliberately not used: no authenticated requests, no credentials, no account, no enumeration of the live API, no traffic to endpoints that process patient data. Every artifact below is one the vendor published on purpose. A teardown of a healthcare platform that probed its live surface would be a different document with a different ethics footing, and this is not that.

02

Findings

Twelve, ordered roughly from structural to strategic. Each states its evidence, its reasoning, and what it is worth to you.

F-01inferred

One origin carries seven jobs

Evidence — EV-04, EV-06, EV-07, EV-08

Every product surface resolves to the single host app.medblocks.com: the dashboard, the REST API, the hosted consent UI, the OAuth callback, the JWKS document, and the MCP server. Content lives elsewhere, on medblocks.com.

The callback path is /api/auth/smart/callback and the key set is at /.well-known/jwks.json. The /api/… prefix, the co-located .well-known route and the JSON 404 from the same origin are the signature of a single application handling both pages and API routes — the Next.js App Router convention being the most likely specific shape, given the first-party SDK is TypeScript.

Worth knowing: there is no separate auth service to point at, no API subdomain, no split between control plane and data plane at the DNS level. For a platform at this stage that is the right call — one deploy, one session story — but it means the consent redirect, the token exchange and the dashboard share a blast radius.
F-02confirmed

They authenticate to Epic with a signed assertion, not a secret — using one RSA-2048 key for the entire platform

Evidence — EV-04, EV-05 · verified by computation

Epic requires a JWKS URI rather than a client secret, which means the client authenticates with private_key_jwt: Medblocks signs a short-lived JWT assertion with a private key, and Epic verifies it against the public key published at the JWKS URL. No shared secret ever transits.

The published key set contains exactly one key. Decoding it confirms the parameters, and the kid turns out to be derivable:

# from the published jwks.json
modulus           256 bytes → RSA-2048
exponent  e=AQAB  → 65537
alg               RS256   use  sig   keys in set  1

# RFC 7638 thumbprint of {"e","kty","n"}, base64url(SHA-256(...))
computed   zoWmCnzEcimOswkElJHSIi6YxU9hnv_7j8TAmv6XypU
published  zoWmCnzEcimOswkElJHSIi6YxU9hnv_7j8TAmv6XypU
           MATCH

A kid that equals the RFC 7638 thumbprint is not something a person types. It is what a JOSE library emits when it generates or imports a key — the behaviour of jose and its siblings in the Node ecosystem. That is a small corroboration of F-01’s TypeScript-backend reading.

Worth knowing: one key pair signs assertions for every workspace, every source and — per the docs — both sandbox and production. Rotation therefore means publishing a second key to the set, waiting for every vendor’s cache to pick it up, and only then retiring the first. Copy the mechanism; think hard before copying the single-key part.
F-03inferred

A single redirect URI serves every tenant, and state is the demultiplexer

Evidence — EV-04, EV-02 (oauth_state_expired), EV-15

The Epic guide instructs you to register one fixed redirect URI: https://app.medblocks.com/api/auth/smart/callback. Not one per workspace, not one per environment. Every authorisation, for every patient, at every hospital, across every customer, returns to that one path.

An OAuth callback receives only an authorisation code and whatever was round-tripped in state. For the platform to know which workspace, patient, source and session a returning browser belongs to — and where to send the patient afterwards — state must be an opaque server-side handle rather than encoded data, because it also has to carry the PKCE verifier, which must never be exposed.

The error taxonomy corroborates this precisely. oauth_state_expired is documented as “OAuth state expired before callback completion.” Something you merely decode cannot expire. Something you look up in a TTL-bounded store can.

Worth knowing: this is the design decision that lets you integrate without registering anything yourself, and it is the one most worth copying. It is also a chokepoint: one route, one state store, and a TTL that silently converts a slow patient into a support ticket.
F-04confirmed

There are two error systems, not one

Evidence — EV-02, EV-06

The documented envelope is rich and stable: type, code, message, param, doc_url, request_id. But an unknown path on the same origin returns something else entirely:

// documented application layer
{ "error": { "type": …, "code": …, "message": …,
             "param": …, "doc_url": …, "request_id": … } }

// actual response from an unrouted path
{ "error": "not_found" }        // application/json;charset=utf-8

A bare string where the contract promises an object. These are two different layers: an outer router that rejects before the API contract applies, and the inner handler stack that honours it.

Worth knowing: if you write a client that assumes error.code is always readable, a typo in a path will hand you undefined instead of a code. Parse defensively at the boundary. And if you are building something similar: make the 404 speak your documented envelope too — it costs one middleware and removes an entire class of confused bug report.
F-05inferred

The 502 class is an inventory of their dependencies

Evidence — EV-02

Error taxonomies leak architecture, because a team only mints a distinct code for a failure mode it actually has to distinguish. Sorting the documented codes by what they reveal produces a clean trust boundary.

The 502 group is the most informative: fhir_error, oauth_error, token_exchange_failed, token_unavailable, storage_error, email_error. Read as a set, that enumerates an EHR FHIR client, an OAuth provider client, a token service, an object-storage adapter and a transactional email provider — five external dependencies, named by their failure.

Meanwhile config_missing (“required server configuration is missing”) sitting in the 500 class is a quiet tell: some per-source configuration is resolved at request time and can be absent, which fits the picture of a source registry populated per vendor and per workspace.

F-06inferred

Nine services, sixteen counted operations — and the shape tells you what is finished

Evidence — EV-07, EV-03, EV-01

A public API directory lists the platform’s services with operation counts. Cross-referencing those counts against the SDK method names and the documentation gives a reasonable reconstruction of the surface — and, more usefully, a map of where the engineering has and has not gone.

Connections cannot be forged, scripted, or bulk-imported; they exist only as the residue of a real human authorisation. That is a correct and deliberate constraint for a system holding delegated access to medical records.
F-07confirmed

Sessions and connections are separate state machines that meet exactly once

Evidence — EV-15, EV-01

Session status (open, complete, expired) is documented as distinct from connection status (active, failed, refresh_failed, and the further expired and disconnected). The sentence that matters: “a session can finish with no connection.”

These are objects with different lifespans. A session is a signed, TTL-bounded link that lives for minutes. A connection is a credential record that lives for months or years and decays through its own failure modes. Collapsing them — the obvious first design — makes it impossible to express a patient who completed the flow and then declined at the portal.

Worth knowing: this is the modelling decision most worth stealing wholesale. If you build this and use one status field, you will discover the need for the second one in production, with live customers, after your API is public.
F-08inferred

The billing meter is enforced in the sync path, not the create path

Evidence — EV-13, EV-02

“A patient counts as ‘active’ the first time we successfully pull FHIR data for them,” and breaching the free cap returns 402 quota_exceeded on new patient sync attempts. Creating a patient record is free and unmetered.

That places the entitlement check inside the pull enqueue or pull completion path, and implies a per-patient marker — a nullable first-successful-pull timestamp is the natural shape — with the workspace’s active count derived from it. A metric measured at the point of value delivered, not at the point of record created.

Worth knowing: it is an unusually honest meter, and it is also good engineering. Failed integrations cost the customer nothing, which removes the main reason not to experiment — and it means their revenue tracks the thing they actually control.
F-09confirmed

The real bottleneck is a browser automation script, and they published it

Evidence — EV-14, EV-04

The Epic registration guide includes browser-console scripts for two steps: selecting the full set of USCDI v3 and read-only R4 scopes, and activating customer organisations — against what the guide names the “7000 clicks problem.”

Epic’s Automatic Client Distribution puts a registered patient app in front of Epic’s customer base, but reaching those organisations means per-organisation activation through a web UI with no bulk API. So the state of the art, for the vendor whose entire business is this, is a snippet you paste into devtools.

Worth knowing: this is the most valuable single fact in the teardown for anyone weighing build against buy. The hard part of healthcare integration is not the OAuth, the FHIR paging, or the normalisation — all of which are tractable engineering. It is thousands of manual clicks in someone else’s admin console, per vendor, forever. That is an operations cost with no technical solution, and it does not appear on any architecture diagram.
F-10inferred

Environment separation is logical, not cryptographic

Evidence — EV-04, EV-09, EV-05

Sandbox and production are presented as strongly separated: different workspaces, different key prefixes (mb_sk_sbx_ versus mb_sk_live_), separate sources, webhooks, exports and history, and a sandbox key that cannot open a session against a production source.

But the Epic guide gives the same JWKS URI for both environments, and the published key set holds one key. So the separation is enforced in application logic over a shared signing identity and — given F-01’s single origin — most likely a shared deployment with a tenant discriminator.

Worth knowing: entirely normal for a platform at this stage, and the logical separation is the part that protects customers day to day. Just size your expectations correctly: “sandbox” here means a different row in a database, not a different system.
F-11inferred

Patient Access is finished; Clinician Workflow is a stub

Evidence — EV-07, EV-01

Count the surface per door. Patient Access has Patients (5 ops), Patient Sessions (2), Connections (2), Events (1) — ten operations, a hosted UI, a dedicated build guide, a quickstart, a per-vendor configuration guide, and four webhook events. Clinician Workflow has one operation — Launch Contexts — and a documentation page that describes what is possible and then directs you to a support form.

The pricing corroborates it: Patient Access is on the free plan; Clinical Workflows and Backend Services are enterprise-only, which is where a feature can be delivered as a partly-manual engagement without anyone noticing. Backend and Network doors have no visible API surface at all.

Worth knowing: the “all four surfaces” positioning is a roadmap claim, not a product claim, and the comparison table it supports should be read that way. If your product needs Door 2 or Door 3, expect a conversation with a human rather than a quickstart — and validate that before you build a plan around it.
F-12speculative

The Clinical Domain Models are openEHR archetypes wearing FHIR clothes

Evidence — EV-12, EV-07, EV-01

The GitHub organisation is an archaeological record of a different company: 62 repositories dominated by Java and openEHR — openFHIR (a bidirectional openEHR↔FHIR mapping engine), a fork of ehrbase (an open-source openEHR server), openehr-sync-service, medblocks-ui web components, plus FHIR server benchmarking and a Couchbase-backed FHIR server. The llms.txt describes bootcamps with 1,100+ students and development services. A Certificates API for verifying training certificates is still listed on the live platform.

The current product is a TypeScript SDK over a Next.js platform selling US regulatory-API integration. That is a pivot from openEHR consultancy and training to a product business, and the old surface has not been fully swept away.

Which makes the “Clinical Domain Models” layer legible in a way the docs never state. Modelling clinical concepts as governed, reusable, terminology-bound structures separate from the transport format is the central idea of openEHR. Their documentation says FHIR is “the transport format” while meaning lives above it — that is archetype thinking, expressed in a FHIR-native product by people who spent years building openEHR tooling.

Worth marking speculative: the lineage is documented; the causal claim about the design is my reading, not theirs. But it predicts something testable — that their normalised models will look more like curated clinical archetypes than like thin FHIR profiles. If you are evaluating this layer, that is the question to ask on the call.
03

What this teardown could not determine

Stated plainly, because a teardown that only lists what it found is selling something.

Unresolved

  • The storage engine. db_error confirms a primary datastore exists and nothing more. Whether the FHIR layer is a bought server, an open-source one, or hand-rolled is not observable from outside — though the couchbase-fhir-ce and fhir-benchmarking repositories suggest the question was researched seriously.
  • The queue or workflow engine. Background pulls are documented as scheduled, retried and resumable. No artifact names what runs them.
  • Whether normalisation is rules or models. The docs describe unit conversion, code-system mapping and aggregation rules. Nothing indicates whether a human curates the mappings, a model proposes them, or both.
  • Tenant isolation below the application layer. F-10 establishes shared signing identity; it says nothing about data-layer isolation, which could be row-level, schema-level or database-level.
  • Actual rate limits. throttled and quota_exceeded exist; no published numbers.
  • Hosting and residency. Not stated publicly. The security page refers you to a contact form for controls detail — which is the normal and correct answer for a platform under a BAA.

Every one of these is answerable in a single call with their engineering team, and all six are worth asking before you commit. The questions are sharper for having done the teardown first.

04

What the teardown changes

Three findings move a decision, and they point in different directions.

Copy these

  • F-03 — one redirect URI, opaque state, server-side lookup. The mechanism that makes multi-tenant OAuth tractable. Give the state a TTL and a named expiry error from day one.
  • F-07 — two state machines. Sessions and connections have different lifespans and different failure modes. One status field cannot carry both.
  • F-06 — no create-connection operation. Make delegated access unforgeable by construction, not by policy.
  • F-02 — asymmetric client auth. Signed assertions over shared secrets, everywhere it is supported. Then do better than one key.

Price these in

  • F-09 — the 7000 clicks. Vendor onboarding is an operations headcount, not a sprint. It is the cost that does not appear in any build estimate and does not go away after launch.
  • F-11 — three of the four doors are thin. If your plan depends on clinician workflow, backend services, or network exchange, verify the surface exists before it becomes a dependency.

The one-line version

Medblocks is a well-modelled multi-tenant OAuth broker with a clinical data layer on top, built as a single TypeScript application, whose genuinely hard problem is not any of its code — it is clicking through Epic’s admin console a few thousand times, which is exactly the kind of work you would want to buy rather than build.

The architecture is copyable in a quarter. The onboarding operation is what you would actually be paying for, and $60,000 a year against a headcount doing that work indefinitely is not a close call for most teams.
