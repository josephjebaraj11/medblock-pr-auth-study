Five Healthcare
Standards

Before we study Medblocks, we need the common terms used in healthcare. These five are the standards everything else rests on — how records are modelled, how they move, and how they get approved and paid.

Part one

What is openEHR?

openEHR is an open standard for storing, exchanging, and managing electronic health records (EHRs) in a way that is interoperable, vendor-neutral, and designed for long-term healthcare data management.

Think of it as

A common language and structure for healthcare data — similar to how HTML provides a standard structure for web pages.

Why was openEHR created?

Traditional healthcare systems often store patient data differently:

The same measurement, three names

  • One hospital stores blood pressure as BP
  • Another stores it as BloodPressure
  • Another stores it in a custom format

This makes sharing and analyzing healthcare data difficult.

openEHR solves this by defining:

  • How clinical data should be structured
  • How it should be stored
  • How different systems can understand the same data

Key concepts

1

Clinical Data Repository (CDR)

The openEHR repository stores patient information in a structured way.

Examples

Patient demographics Lab results Diagnoses Medications Vital signs Clinical notes
2

Archetypes

An archetype is a reusable clinical data model.

Instead of every hospital creating its own blood pressure structure, everyone uses the same archetype.

3

Templates

Templates combine multiple archetypes for a specific use case.

A single clinic visit needs several kinds of measurement at once. The template says which archetypes that visit uses, and in what order.

Part two

What is FHIR?

FHIR — Fast Healthcare Interoperability Resources — is a healthcare data standard created by HL7 International to help different healthcare systems exchange medical information in a consistent way.

It is one of the most widely adopted healthcare interoperability standards today.

Simple explanation

Imagine:

  • Hospital A uses one software system
  • Hospital B uses another
  • The insurance company uses a third
  • The lab uses a fourth

FHIR provides a common API and data format so they can communicate without custom integrations.

Think of FHIR as
Healthcare + REST API + JSON

For developers, it feels very similar to modern web APIs.

Example: Patient resource

FHIR data is organised into resources — self-contained objects like Patient, Observation, Condition or MedicationRequest. Here is the simplest one:

{
  "resourceType": "Patient",
  "id": "123",
  "name": [{
    "family": "Doe",
    "given": ["John"]
  }],
  "gender": "male",
  "birthDate": "1990-01-01"
}

In FHIR, family is the surname and given holds the forenames — given is an array because a person can have several. So this resource describes John Doe. It is an easy pair to swap by accident, and worth getting right early, because every other resource points at patients by id and displays them by name.

Plain JSON, a predictable shape, fetched over ordinary HTTP. That is the entire reason FHIR spread as fast as it did — any developer who has used a REST API already knows how to read it.

Part three

What is CRD?

CRD — Coverage Requirements Discovery — is a healthcare standard that helps a doctor know whether an insurance company requires prior authorization before a treatment, test, or medication is ordered.

Simple analogy

Imagine you are shopping online. You add a product to your cart, and before checkout the website tells you: this item needs additional approval · please upload a document · you are eligible for a discount.

CRD does something similar for healthcare.

When a doctor orders a treatment, the hospital's EHR system automatically checks with the insurance company and tells the doctor:

  • Does this need prior authorization?
  • What documents are required?
  • Are there alternative treatments that don't need approval?

Example

Without CRD

  1. Doctor orders an MRI scan.
  2. Staff submits the request to insurance.
  3. Insurance replies: prior authorization is required.
  4. Staff gathers documents and resubmits.
  5. Several days are lost.

With CRD

  1. Doctor orders an MRI in the EHR.
  2. CRD immediately checks the insurance rules.
  3. A message appears in the chart.
Message shown to the doctor

“This MRI requires prior authorization. Please provide recent clinical notes and imaging history.”

The doctor knows the requirements instantly and can start the authorization process right away.

Where CRD fits

How it actually works

CRD is not a separate system the hospital buys. It is built on the two things you have already met: FHIR for the data, and CDS Hooks for the moment. When the doctor places the order, the EHR fires a hook — order-select or order-sign — to the payer's service, which answers with a card: a short message rendered right there in the chart.

It comes from HL7's Da Vinci project, a set of FHIR standards aimed squarely at the payer–provider gap. CRD is the first link in a chain of them — which is Part four.

Part four

What are CDS Hooks?

CDS Hooks — Clinical Decision Support Hooks — is a standard that allows an EHR system to ask another system for advice at specific moments during a doctor's workflow.

Think of it as

Google Maps suggestions while you're driving. Maps can pop up traffic ahead or take an alternate route — not because you asked, but because you reached a moment where the advice was useful.

Similarly, while a doctor is working in the EHR, CDS Hooks can pop up: this medication may interact with another medication · prior authorization is required · this patient may qualify for a specific treatment.

Simple example

A doctor orders an MRI. Three things happen, and the doctor experiences them as one.

  1. The doctor clicks “Order MRI”. The EHR notices a specific event occurred.
  2. The EHR asks for guidance. It sends patient and order information to a CDS service.
  3. The CDS service responds with a card — a short message rendered right there in the chart.
Card returned to the EHR

Prior authorization is required for this MRI.

Required documents:

  • Clinical notes
  • Previous imaging reports

The doctor sees this information immediately.

Why it matters for prior authorization

CDS Hooks is often the mechanism used to trigger CRD. The doctor places an order, the hook fires, the CRD service answers, and the prior-authorization requirements appear. The two standards answer different questions:

CDS Hooks“When should we ask for advice?”
CRD“What advice should we give about insurance coverage and prior authorization?”

Another real-world example

A doctor prescribes an expensive medication. CDS Hooks displays:

Warning · card

This medication requires prior authorization.

Alternative covered medications:

  • Drug A
  • Drug B

The doctor can decide whether to proceed or choose an alternative — at the moment the decision is being made, rather than a week later when a rejection letter arrives.

Common CDS Hooks

A hook is just a named moment. These four cover most of what a payer or decision-support service cares about:

HookWhen it runs
patient-viewWhen a patient's chart is opened
medication-prescribeWhen a medication is prescribed
order-selectWhen a lab test, imaging study, or procedure is selected
order-signJust before the order is finalized

How CDS Hooks, CRD, DTR and PAS fit together

Each one hands off to the next. CDS Hooks provides the moment; the three Da Vinci standards provide the answer, the paperwork, and the submission.

Part five

What are X12 transactions?

X12 transactions are standardized electronic message formats used in the U.S. healthcare industry to exchange information between hospitals, clinics, insurance companies, pharmacies, and other healthcare organizations.

Think of them as

Predefined forms that computers use to talk to each other.

Imagine sending money through a bank. The bank expects the information in a specific format — account number, amount, recipient, date. If everyone uses the same format, banks can process transactions automatically. Healthcare works the same way: instead of paper forms, organizations send X12 transactions.

Real-world example

A doctor performs an MRI for a patient. The hospital sends an X12 transaction to the insurance company, and the insurance company processes it and sends another one back.

Common healthcare X12 transactions

Most of them come in request-and-response pairs — you send one number, you get a different number back.

TransactionPurpose
270Ask insurance if a patient is eligible for coverage
271Eligibility response
276Ask about claim status
277Claim status response
278Prior authorization request and response
837Healthcare claim submission
835Payment and remittance details

Example: prior authorization using X12 278

Before treatment, the hospital sends an X12 278 request. In plain language it asks:

X12 278 · request

“Can this patient receive this procedure, and will you cover it?”

The insurance company replies with an X12 278 response, which means one of three things:

X12 278 · response

Approved  ·  Denied  ·  Need more information

How it fits with CRD, DTR and PAS

Modern FHIR-based prior authorization workflows still have to interact with older insurance systems. The new standards run all the way up to the point of submission — and then the request is translated into X12 278, because that is what most insurers can actually receive.

CRDChecks if authorization is needed.
DTRCollects the required information.
PASSubmits the authorization request.
X12 278The format many insurers still use to receive that request.

Why X12 is important

Most U.S. insurance companies have used X12 standards for decades. Even though healthcare is moving toward FHIR, many insurers still process claims (837), payments (835), eligibility checks (270/271) and prior authorizations (278) as X12 transactions.

That installed base is why X12 will not simply disappear. It is also why the rules are changing around it rather than through it: under the 2027 prior authorization rule, X12 278 becomes optional for organisations that have implemented the FHIR route — regulators applying pressure to the old format rather than switching it off.

Part six

How the two fit together

They are often presented as rivals. They are not — they answer different questions, and a serious platform usually uses both.

CDS Hooks and CRD both sit in the FHIR column: they are built on FHIR resources carried over ordinary HTTP, so they inherit the REST-and-JSON world rather than the archetype one.

X12 belongs to neither column. It is the older EDI world that both of these standards are gradually growing over — still carrying most of the money and most of the prior authorizations in US healthcare, and still sitting at the far end of every FHIR workflow that touches a payer.

One way to hold it

openEHR is closer to your database schema — careful, clinically governed, built to outlive the software using it. FHIR is closer to your API layer — the shape data takes when it travels between systems.

Why this matters before studying Medblocks

Medblocks’ own documentation makes a claim that only lands once you know both terms: “FHIR is the transport format, but source data still varies.”

Every US hospital now exposes FHIR — that is the left-to-right arrow in the diagram above, and it is solved. What is not solved is that the same clinical fact arrives from five hospitals in five shapes, five code systems and five units. Medblocks’ answer is a layer they call Clinical Domain Models, sitting above raw FHIR.

That is archetype thinking. Hold both ideas — FHIR for the wire, archetypes for the meaning — and the rest of the Medblocks study reads as one continuous argument instead of a pile of acronyms.
